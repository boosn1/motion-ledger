# motion-ledger 踩坑清单

来源：2026-11-21《星光 · 延时》75s / 1920×1080 / 30fps 全流程（从需求确认到 Concat 交付）。全部条目都是本会话**真实发生并被实测确认**的，不是推测。

每条写五段：**现象 / 触发场景 / 当时的错误判断 / 正确做法 / 可复用结论**。

分八类：A 路线与工具链 · B 门禁 · C 动效与视觉 · D 音频 · E 交付层 · F 文案与排版 · G 数据与诊断 · H 仓库与同步。

## A. 路线与工具链

### A1. 「本机没 Chrome」被当成「Remotion 不可用」

- **现象**：开工时判定 Remotion 不可用，改用自写光栅路线；用户事后问「没有用 Remotion 吗，为什么不用」。
- **触发场景**：`Test-Path "C:\Program Files\Google\Chrome\Application\chrome.exe"` 与 x86 版都返回 `False`。
- **当时的错误判断**：Remotion 依赖系统 Chrome → 系统没有 → 这条路线走不通。
- **正确做法**：Remotion **自带** headless 浏览器，在 `templates/remotion-starter/node_modules/.remotion/chrome-headless-shell/win64/chrome-headless-shell-win64/chrome-headless-shell.exe`（实测 260,766,720 字节）。检查顺序是「`node_modules` 在不在 → `.remotion/chrome-headless-shell` 在不在 → 真渲 30 帧能不能出片」，**系统 Chrome 从来不是判据**。
- **可复用结论**：任何「某工具能不能用」的判断，必须落到**该工具自己的运行时依赖**上，并且用**真跑一次**收尾。查系统级同类软件是查错了对象。

### A2. 门禁脚本必须从仓库根跑

- **现象**：`cd templates/node-starter` 之后跑 `node verify/../../verify/film.mjs ...` → `MODULE_NOT_FOUND`，栈里 `requireStack: []`。
- **触发场景**：想省事在模板目录里直接跑门禁。
- **当时的错误判断**：`verify/` 里的脚本用相对路径 `../../verify/...` 总能找到自己。
- **正确做法**：`cd` 回仓库根，用完整相对路径传参：
  ```powershell
  node verify/film.mjs --film templates/node-starter/out/film.mp4 `
    --spec templates/node-starter/src/spec.mjs --ledger templates/node-starter/LEDGER.md
  ```
- **可复用结论**：门禁脚本内部会 `import` 同目录的 `lib.mjs`，`import` 的解析基准是**脚本自身位置**而不是 cwd——但只要调用路径里混了 `..`，Node 在 ESM/CJS 混用场景下就会解析失败。规则：**门禁一律从仓库根调用，参数给相对仓库根的路径。**

### A3. `ffmpeg -f f32le pipe:0` 在 pwsh 下失败

- **现象**：`ffmpeg -v error -i x.wav -ac 1 -ar 48000 -f f32le pipe:0 | node xxx.mjs` → `Bad file descriptor`，拿不到数据。
- **触发场景**：想把音频解码成原始 float 交给 Node 做频谱分析。
- **当时的错误判断**：管道 stdout 应该能像 Linux 一样直接接。
- **正确做法**：先落盘再读，多花一次 IO 但一定成功：
  ```powershell
  ffmpeg -v error -y -i public/score.wav -ac 1 -ar 48000 -f f32le out/check/ours.f32
  ```
  ```js
  const buf = readFileSync('out/check/ours.f32');
  const f32 = new Float32Array(buf.buffer, buf.byteOffset, buf.length / 4);
  ```
- **可复用结论**：Windows 上让 ffmpeg 往 stdout 吐二进制、再由 Node 读管道，是不可靠的。**音频分析一律落 `.f32` 中间文件**（放 `out/check/`，天然被 gitignore）。

### A4. `@napi-rs/canvas` 同一 canvas 二次 `data()` 会失效

- **现象**：`DOMException [IndexSizeError]: The canvas has no pixels.`
- **触发场景**：在一个循环里对同一个 `canvas` 调两次 `c.data()`（第一次取像素算指标、第二次再取一次做别的统计）。
- **当时的错误判断**：`data()` 是纯读操作，可以反复调。
- **正确做法**：**一次取，存到变量里复用**：
  ```js
  const px = c.data();      // 只取一次
  ... 用 px 做所有统计 ...
  ```
- **可复用结论**：native canvas 的 `data()` 是「导出当前像素缓冲」的一次性语义，第二次调用前必须重新绘制。批量对比多帧时，每帧一个新 canvas。

## B. 门禁

### B1. 台账覆盖率缺的是「不落成数字的条款」

- **现象**：`verify/spec.mjs` 报「台账覆盖率 48/53」，缺 S29/S30/S34/S35/S36。
- **触发场景**：这五条约束的是「整个文件的写法」（阅读窗 0.25s/汉字、主题、材质世界、禁 glow/粒子/交叉淡化、禁无动机渐变），没有对应的常量可标注。
- **当时的错误判断**：以为要在源码里找一个数字挂上去。
- **正确做法**：在 `src/spec.mjs` 文件头的注释块里逐条写出 id 与它约束什么。`collectSourceIds` 用 `/\b([SXE])(\d{2,4})\b/g` 扫**源码任意位置**，注释里的 `S29` 也算回写。
- **可复用结论**：台账回写不要求「id 旁边有数字」，只要求 **id 出现在源码里**。约束写法的条款，就写进文件头注释——那是它唯一合理的落地位置。

### B2. 未记账常量只是 warn，禁用项才是 FAIL

- **现象**：`export const STARS` 报「未记账常量」，但退出码仍是 0；而 `Date.now` 报「禁用项」直接把退出码变成 1。
- **触发场景**：`render.mjs` 里用 `Date.now()` 打印渲染进度与耗时。
- **当时的错误判断**：以为打印进度也会被拦。
- **正确做法**：`scanConstants` 只查**行首无缩进**的顶层 `const`；豁免有四种——箭头函数/`= function`（机制不是设计）、容器内成员已带 id、行尾 `// ledger-allow: 理由`、文件头 12 行内 `ledger-file-allow: 理由`。给三处 `Date.now()` 各加行尾 `// ledger-allow: 只用于打印进度与耗时，不参与任何画面内容`。
- **可复用结论**：**「未记账」是提醒你补 id，「禁用项」是拒绝保存。** 前者可以欠着，后者不能。豁免注释必须写理由，理由要能被第三个人判断真假。

### B3. `FILM` 必须是单行字段形式的 `const FILM = {...};`

- **现象**：门禁报「格式对 spec」失败或读到 `duration: NaN`。
- **触发场景**：把 `FILM` 写成嵌套对象、或在字段之间夹了多行注释块。
- **当时的错误判断**：JS 对象怎么写都行。
- **正确做法**：`parseSpec` 用 `(?:const|let|var)\s+FILM\b` 定位，再用 `\}\s*;` 或「空行 + export/const」截断，然后逐字段 `num(key)` 正则匹配 `duration\s*:\s*([\d.]+)`。所以必须写成：
  ```js
  const FILM = {
    duration: 75,
    fps: 30,
    width: 1920,
    height: 1080,
    loop: false,
    sound: true,
  };
  ```
- **可复用结论**：**门禁是正则解析器，不是 JS 解释器**。任何「机器要读的常量块」都要写成最朴素的形式，别用展开运算符、计算属性、嵌套对象。

### B4. 峰值窗口表覆盖不全 → 计划内运动被误报

- **现象**：`verify/film.mjs` 报「165 处计划外尖峰」。
- **触发场景**：台账 `### 计划内运动峰值` 只有 6 行，而片子里有 20 多个运动片段。
- **当时的错误判断**：先怀疑是画面真有 bug，逐个包围盒去查。
- **正确做法**：两步。①先查真缺陷（见 C1：环境呼吸取整闪烁，那是真 bug，要修）；②再按**真实设计的运动片段**把表补全，并在表头写一句「这张表是设计里的运动片段全集，不是给门禁开后门：每一行都必须对应 S 表或 X 表里的一条已声明动作」。最终 21 行，209 处峰值全部落表内。
- **可复用结论**：**门禁不说「这里不该动」，它说「你没声明」。** 补表不是作弊，但每一行都要能指回一条已声明的设计动作，否则表就退化成橡皮图章。

### B5. 静止窗口的边界：设计 vs 缺陷

- **现象**：`### 计划内静止 72.40–75.00` 声明了收尾 hold，但该区间内仍有尖峰报错。
- **触发场景**：收尾段全帧无元素运动，却每 0.87s 全帧跳 1 级亮度。
- **当时的错误判断**：既然已声明静止，报错就是门禁口径问题。
- **正确做法**：查出是 `sky()` 的整幅亮度正弦（C1），**修掉它**，而不是靠声明掩盖。
- **可复用结论**：**声明窗口只豁免「计划内的运动」，不豁免「未种子噪声」。** 收尾段的闪烁等价于「画面在抖」，那是缺陷不是设计。

## C. 动效与视觉

### C1. 8 位量化 + 整幅亮度正弦 = 每 0.87s 整帧跳 1 级

- **现象**：安静段落的逐帧差中位数 1.286e-4，收尾 hold 内每隔约 0.87s 出现一次全帧跳变（`max=1.90e-3`，中位 0）。
- **触发场景**：`sky()` 用 `const breath = Math.sin(t * 0.52) * 2.2;` 对整幅渐变三段分别 `hexShift(..., breath)`。
- **当时的错误判断**：以为这是「环境呼吸」，是设计的一部分。
- **正确做法**：整幅亮度调制在 8 位输出上，每帧 delta 只有 0.038 级，攒 26 帧才跨一次整数边界——那**不是呼吸，是未种子闪烁**。改成：底色固定三段渐变，生机交给地平线辉光带的强度脉冲 `pulse = 0.5 + 0.12 * Math.sin(t * Math.PI)`（周期 2s，与 60 BPM 谱面同拍）。
- **可复用结论**：**任何「整幅」级别的连续量（亮度、色相、对比度）在 8 位输出上都会退化成阶梯跳变。** 要呼吸就呼吸**局部几何或局部 alpha**，不要呼吸全幅亮度。

### C2. 不能简单删掉呼吸——会把 median 打到 0

- **现象**：试着把环境呼吸彻底删掉，门禁反而报所有帧都是尖峰。
- **触发场景**：`spikeThreshold = 4 * median(v)`，**没有绝对地板**。
- **当时的错误判断**：静止 = 最安全。
- **正确做法**：保留一个「每帧都在跨量化边界」的极小幅度活动（实测方案 G：渐变分界 ±0.09、辉光上沿 ±0.07，`med=1.32e-5`、`spikes=0/240`）。幅度太小（`med=7e-6`）会让全片 median 被别的元素撑高后重新触发尖峰判定。
- **可复用结论**：**门禁的阈值是相对的（中位数的倍数），所以「完全静止」会让分母归零。** 需要一层持续存在、幅度稳定、不与元素抢注意力的底噪活动。

### C3. 同相呼吸让整屏同时跨量化边界

- **现象**：网格线 alpha 用共享的 `0.045 + 0.006*sin(t*0.565)` 时，整屏网格会同时跳。
- **触发场景**：所有线共用同一个相位。
- **当时的错误判断**：一条线在呼吸，加总也是呼吸。
- **正确做法**：每条线自己的相位——`0.045 + 0.006*Math.sin(t*0.565 + i*0.83)`（竖线）、`+ 1.7 + j*0.83`（横线）。错相位后每帧只有一两条线在跨界。
- **可复用结论**：**批量元素做同类微动时，相位必须按索引打散。** 同相 = 一次事件；错相 = 持续活动。

### C4. 统一 progress 的 morph 会「先排到位、后缩尺寸」

- **现象**：57.4s 处 8 个水平椭圆互相穿插成三连环，右数第 5/6/7 个圆心间距小于直径。
- **触发场景**：X04（光壳 → 母题线刻度）用统一系数 `0.2694` 做 `morphPts`，只保证「周长总和 = 1584px」。
- **当时的错误判断**：周长守恒就等价于不重叠。
- **正确做法**：把半径压缩与位移拆成两条曲线，**半径先缩、位移匀速**：
  ```js
  const p  = prog(t, T.x04[0], T.x04[1] - T.x04[0], EASE.inOut);
  const pr = 1 - Math.pow(1 - p, 2.5);   // 半径：先快后慢
  const cx = lerp(GEO.starCx, lerp(GEO.motifX0, GEO.motifX1, tt), p);  // 位移：匀速
  const a  = lerp(r0, GEO.tickHalfH, pr);
  const b  = lerp(r0, Math.max(2.4, r0 * GEO.tickLenK), pr);
  ```
  任何一帧都满足「半径 < 半个间距」。
- **可复用结论**：**「不重叠」是几何约束，不是面积/周长约束。** 多个同源形状散开时，缩小的进度必须领先于位移的进度。

### C5. 膨胀中的轮廓直接 `fill` = 一块圆盘

- **现象**：42.7s 处左上出现一个巨大的金色实心圆盘，而设计是「光壳」。
- **触发场景**：X03 段对膨胀中的 128 点轮廓用 `poly(ctx, pts, {fill: ...})`。
- **当时的错误判断**：轮廓是圆的，填出来就是圆环。
- **正确做法**：用**真差集**出环带——外圈顺时针 + 内圈逆时针，nonzero winding 自动挖空，带宽可控：
  ```js
  function bandFill(ctx, pts, w, color, alpha) {
    const cx = ..., cy = ...;                 // 质心
    const k = Math.max(0, 1 - w / len);       // 内圈收缩比
    poly(ctx, pts, { fill: color, alpha });             // 外圈顺时针
    poly(ctx, inner.reverse(), { fill: color, alpha }); // 内圈逆时针
  }
  // X03 段：带宽 24 → 1.6
  bandFill(ctx, pts, lerp(24, 1.6, p3), rgba(COLOR.gold, 0.92), 0.92);
  ```
- **可复用结论**：**「环」和「盘」差一条规则：内圈要反向绕。** 用透明度假装空心会在背景有星点时露馅。

### C6. 形变的计时起点写错 → 半径突缩一帧

- **现象**：42.8s 那帧光壳半径从 203 突然缩回 194，明明在往外走却跳一下。
- **触发场景**：`shellR(i,t)` 的 `grown` 从 `T.x03[1]`（42.8s）起算，而 X03 的膨胀其实从 `T.x03[0]`（40.0s）就开始。
- **当时的错误判断**：形变段结束（`x03[1]`）才是膨胀的起点。
- **正确做法**：`const grown = Math.max(0, Math.min(t, T.x04[0]) - T.x03[0]);`
- **可复用结论**：**一个量被两个阶段共用时，计时起点必须回到它真正的物理起点。** 交接处的一帧突跳是最容易被观众抓到的地方。

### C7. 文字退场「一帧硬消失」，而旁边的线是平滑退的

- **现象**：43.41s 四个刻度数字 `ink 201 → 0` 一帧内全消失，同帧基线还在 `455 → 383` 缓降、缘线 `2661 → 2545` 缓降。40.02s 读数「2025 年」整块 `2023 → 0` 一帧完成。
- **触发场景**：文字用 `if (pout < 1) drawText(...)` 之类的时间闸门控制显隐，线用 `alpha * (1-pout)`。
- **当时的错误判断**：只要都在同一秒内消失，观众不会注意差别。
- **正确做法**：**全片文字退场统一成遮罩擦除**——`textMasked` 逐字位移 `loff = -pout * 118`，0.3–0.4s，与左侧文案同一套手法；退场起点比线早 0.2s（`T.rulerLabelOut = 42.6` vs 基线 `42.8`），这样「字先走、线后收」，因果顺序读得出来。
- **可复用结论**：**同一个场景里，同类元素的退场手法必须统一。** 线在慢慢退、字凭空没了，是全片唯一还「一眼假」的地方——这条被独立复审明确点为一票否决项。

### C8. 用透明度淡入代替遮罩

- **现象**：文案逐字淡入看起来像「整体浮上来」，没有「一个字一个字升起来」的节奏。
- **触发场景**：`ctx.globalAlpha = p` 配合 `fillText`。
- **当时的错误判断**：透明度渐变就是淡入。
- **正确做法**：`textMasked(ctx, str, x, y, { offs })`——逐字给一个垂直位移，用 `clip` 把位移超出区域的部分裁掉，字从下往上「长出来」。`offs` 按字符索引错开 0.055s（入场）/ 0.028s（滚出）。
- **可复用结论**：**遮罩是「被边界切掉」，透明度是「整体变淡」。** 前者有方向感和节奏，后者只有浓度。

### C9. 片名的 CJK 中点在大字号下渲成实心圆饼

- **现象**：72.6s 片名「星光 · 延时」中间的「·」变成一个 φ≈46px 的实心圆饼，还压在母题线上。
- **触发场景**：200px 字号的 CJK 字体里，「·」的字形本身就是实心圆，放大后失去「间隔号」的语义。
- **当时的错误判断**：直接用 `textRun('星光 · 延时')` 一行画完。
- **正确做法**：**拆两段 + 独立圆点**——按 `·` 拆开，`measureRun` 算左段宽度，中间画 `disc(r = size * 0.075)`，`dotGap = size * 0.62`，两段各自 `textMasked`，圆点 `EASE.out` 从 0 长出 0.5s。台账补一条 **E13** 声明它（否则就是「未记账的装饰元素」）。
- **可复用结论**：**大字号下，标点要当图形重画，不能靠字形。** 而且重画出来的图形必须进台账——它已经是设计元素，不是文字。

### C10. 读数与图形标记叠印

- **现象**：39.0–39.6s 大数字「2025」左缘 x=1520 与观测者标记（1560,700 十字+外环）直接叠印，外环弧线压在「2」字身上。
- **触发场景**：读数右对齐到 x=1752，观测者标记固定在 x=1560。
- **当时的错误判断**：两个元素在不同图层，先画后画就能分开。
- **正确做法**：给读数块让出 x 区间——观测者标记与光带/尺子的右端统一左移到 `1490`，读数右缘仍 1752，间隔 15px。
- **可复用结论**：**「不同图层」不等于「不重叠」。** 布局阶段就要给每个可变量算最坏情况的包围盒（数字位数最多的那一帧）。

### C11. 刻度标签被图形圈住 / 被线穿字

- **现象**：`0` 标签被套在星上的观测环（r=44）圈住；`640` 标签被右端垂线从字中间穿过。
- **触发场景**：所有刻度标签统一 `center` 对齐 `rulerY + 44`。
- **当时的错误判断**：统一对齐看起来最整齐。
- **正确做法**：两端特殊处理——`0` 挪到 `x-20, rulerY+66` 右对齐（躲开观测环）；`640` 改成 `x-12` 右对齐（停在垂线左侧）；其余仍居中。
- **可复用结论**：**首尾标签永远要单独排。** 中间元素可以吃统一规则，端点会撞上「尺子的边界物」（环、垂线、箭头）。

### C12. 辅助线画得太早 → 悬 14 秒指向空处

- **现象**：尺子 14s 就长好，右端垂线也在那时画出，但它指向的观测者 28.6s 才入场，中间 14 秒是一根没有意义的线。
- **触发场景**：垂线起点用 `T.rulerIn + T.rulerDur * 0.85`（跟着尺子长完）。
- **当时的错误判断**：垂线是尺子的一部分，尺子画完就该有。
- **正确做法**：垂线起点改成 `T.obsMarkIn`（观测者入场那一刻）。
- **可复用结论**：**每个元素的出现时刻应该是「它开始有意义」的时刻，不是「它所属组件的完成时刻」。**

### C13. 收回太晚 → 光已离开光源，尺子还指着空处

- **现象**：43–56s 光壳已膨胀到 r≈273，但光带两条缘线与刻度数字 0/160/320/480/640 全部滞留到 56s 才收回，52s 帧里「640」仍清晰压在光壳右侧。持续 13 秒。
- **触发场景**：`T.bandOut = 55.0`、`T.rulerOut = 55.4`（跟着下一场切换走）。
- **当时的错误判断**：等下一场开始时统一清场更整齐。
- **正确做法**：`T.bandOut`/`T.rulerOut` 全部提前到 **42.8s**（X03 结束当场收回）——光壳已离开光源，再留着就是「指着空处」。这是独立复审认定的最严重问题，也是全片唯一一处观众能直接看出物理上讲不通的地方。
- **可复用结论**：**退场时机由「因果关系是否还成立」决定，不由「下一场什么时候开始」决定。**

### C14. 元素之间没有动作 → 死区

- **现象**：`verify/film.mjs` 报「中段有死区 从 59.83s 起静止 2.77s > 1.5s」。
- **触发场景**：l5a(59.2) 与 l5b(62.6) 两句文案各自升起后，到 67.0 滚出前画面只有母题线不动。
- **当时的错误判断**：先把 l5b 提前到 61.0 缩短间隔。
- **正确做法**：提前反而变成 61.73 起静止 3.80s（两句都升起后更长的空白）——**改回 62.6**，改给母题线加一枚**读头**：`scan = prog(t, T.motifIn + T.motifDur + 1.0, 6.2, EASE.linear)`（59.6–65.8s），读头 `seg(sx, motifY-26, sx, motifY+26)`，扫过的珠子亮一档。台账 E09 补第④特征。
- **可复用结论**：**消灭死区要「加一个有语义的动作」，不是「缩短间隔」。** 缩短间隔只是把两块空白挤成一块。读头的语义是「在扫描」，所以它动 6 秒也不闷。

### C15. 靠拉长滚动来消死区，是错的方向

- **现象**：把 `READ[0].roll` 从 6.0 拉到 8.2，最长静止降到 0.53s，但数字 8.2 秒一直在爬、永不停。
- **触发场景**：读数滚完后到下一句文案之间有 2 秒空白。
- **当时的错误判断**：数字在动 = 有运动 = 没死区。
- **正确做法**：**改回落 6.0**，在数字滚到终值那一刻加一个**落定手势**——下划线从左往右划出 0.55s：
  ```js
  const pul = prog(t, w.from + w.roll, 0.55, EASE.out);
  if (pul > 0) seg(ctx, readX - 320, readY + 22, readX - 320 + 320 * pul, readY + 22, COLOR.cold, 1, 0.34);
  ```
  停住因此不是「没事发生」，而是「刚刚确认过」。
- **可复用结论**：**「数字还在爬」是假运动，观众读到的是「它算不完」。** 真正的解法是给「停住」一个仪式——确认、落章、划勾。

### C16. 光壳最外圈越过安全边

- **现象**：55.2s 光壳左缘到 x=183，越过 S 表声明的 120px 安全边 63px，距文案左缘 168 只剩 15px。
- **触发场景**：`GEO.shellGrow = 6`（6px/s 匀速外扩）。
- **当时的错误判断**：外扩越远越有「光在扩散」的气势。
- **正确做法**：`shellGrow` 改成 **3.4**——最外圈 42.8→56.0s 长到 r≈239，左缘 213，守住 168 文案线。
- **可复用结论**：**匀速外扩必须用「最远时刻 + 最坏方向」反算速度**，而不是先定速度再看到哪。

## D. 音频

### D1. pad 恒定电平铺满整段 = 律动差的真正病根

- **现象**：用户反馈「律动方面和画面结合的不是很好」；实测脉冲对比度（每 0.75s 窗口内 100ms 窗 RMS 最高-最低）中位只有 9.5dB，而参考片 18.3dB。
- **触发场景**：`bed` 里 pad 以 `dur: 75` 整段铺满，`mix` 只压到 -2.1dB。
- **当时的错误判断**：音符不够密 → 加音符。
- **正确做法**：参考片 pad 只有 **-31.6dB**（几乎听不见），连续感靠的是**一条持续跑动的琶音**。把 pad 压到 -13.0dB 后，对比度 10.1 → 16.4 → 17.1dB。
- **可复用结论**：**「律动差」先查长音层的电平，不是先加音符。** 一个恒定电平的长音会让所有脉冲只是「叠一下」，格子之间永远没有空隙。

### D2. 侧链退让（ducking）救不了「每格叠满」

- **现象**：加了 ducking（按事件时刻给 pad/bass/ambience 打坑，-7.5dB、atk 55ms、rel 300ms），对比度只从 9.5 升到 9.7dB。
- **触发场景**：每格叠 4–5 个音（265 事件/75s = 3.5 个/秒，参考片 1.32）。
- **当时的错误判断**：有坑就有对比。
- **正确做法**：先保证「一格一个音」（格号 %4 分工），再谈 ducking；最终参数 `depth = -20dB`、`atk = 0.04`、`rel = 0.62`。
- **可复用结论**：**ducking 是「让持续音给打击让路」，前提是打击之间真有路。** 编曲密度没降下来之前，坑会被别的层填平。

### D3. `whoosh` 包络起点能量为 0

- **现象**：文案升起那刻声音反而掉 10.3dB。
- **触发场景**：`whoosh` 用 `Math.sin(Math.PI * Math.min(1, t/dur)) ** 2`，默认 `dur: 0.8` → 0.4s 才到峰值，起点是 0。
- **当时的错误判断**：whoosh 是「切换音」，给切换点挂上就对。
- **正确做法**：文案升起改配 **bell**（3ms 攻击）+ whoosh 的 `dur` 压到 0.45；非格点的画面动作再补一枚 `tick` 硬起音。
- **可复用结论**：**判断一个音效「有没有咬住画面」，看的是它起点的能量，不是它峰值的位置。** 包络从 0 开始的效果，不能用在「必须在这一帧响」的地方。

### D4. `bell` 衰减太长会盖住后续落点

- **现象**：43.0s 的钟把 43.2s 与 44.3s 两个落点盖住。
- **触发场景**：`const env = Math.exp(-t / 0.9) * Math.min(1, t / 0.003);` —— 0.9 的尾音 2 秒才到 -20dB。
- **当时的错误判断**：钟就该有余韵。
- **正确做法**：衰减改 **0.42**（仍有约 1.2s 可闻余韵，但不会糊住 0.2–1.5s 内的下一次起音）。
- **可复用结论**：**衰减时间要按「最近的两个事件间隔」反算**，不能凭「钟声应该长」的直觉。

### D5. 母版链 EQ 会在编曲结构变化后失效

- **现象**：频谱质心 6800–10000Hz，参考片 500–4000Hz，听感薄、刺、沙。
- **触发场景**：旧母版链 `peak 260 -3.5 / peak 750 -2.0 / highshelf 2400 +2.5`，是在 pad 占九层总功率 76.4% 时做的补偿；pad 降到 10% 后，这套补偿变成「把中频挖空、只剩高频」。
- **当时的错误判断**：母版链是「定好就不用动」的。
- **正确做法**：按八度带实测重做——`highpass 38 → peak 58 +7.0 → peak 130 -3.0 → peak 260 -6.5 → peak 640 -5.0 → highshelf 2400 -3.5 → highshelf 8000 -6.0 → limiter`。40–80Hz 12.9%→36.8%（参考 43.7%），10–20kHz 2.8%→0.4%（参考 0.2%）。
- **可复用结论**：**母版链是针对某一版编曲调出来的，编曲结构变了就必须重测。** 判据用八度带能量分布，不用「听起来亮不亮」。

### D6. `cues.mix` 的 dB 必须乘在合成阶段

- **现象**：只压分轨会造成「试听版安静、交付版仍吵」的分裂。
- **触发场景**：想通过改 `public/stems/*.wav` 来调层音量。
- **当时的错误判断**：分轨是交付用的，改分轨最直接。
- **正确做法**：`mix` 的 dB 乘进 `synth()` 的 `addNote`（`const v = fn(...) * mixG`），母版与分轨同时受影响；分轨 WAV 本身不动（动了会削顶、失去诊断价值）。桥接脚本读 `stems.json` 的 `suggestGain` 设 clip.volume。
- **可复用结论**：**音量只有一个真相源。** 在合成阶段乘系数，两条输出路径才一致。

### D7. 琶音踩在格点上会与 kick 撞

- **现象**：加了琶音后听感「更响但没更密」。
- **触发场景**：琶音与鼓共用 0.75s 网格。
- **当时的错误判断**：对齐网格才整齐。
- **正确做法**：琶音用 `ARP_STEP = 0.375`、`ARP_OFFSET = 0.1875`（落在脉冲网格正中间），交替成「哒-叮-哒-叮」。参考项目实测过「58.6% 的起音能量砸在同一格」这个数字。
- **可复用结论**：**两个节奏层要产生「律动」，相位必须错开半格。** 同格叠加只会更响。

### D8. `loudnorm` 一遍法会过冲

- **现象**：`-af "loudnorm=I=-16:TP=-1.5:LRA=9"` 一次跑完，实测 -14.7 LUFS（目标 -16）。
- **触发场景**：线性模式下的动态归一化，测量值与目标值互相追赶。
- **当时的错误判断**：给了 `I=-16` 就会到 -16。
- **正确做法**：**两遍法**——先跑一遍 `print_format=json` 拿 `input_i / input_tp / input_lra / input_thresh / target_offset`，再带 `measured_*` 与 `offset`、`linear=true` 跑第二遍。实测得 -15.7 LUFS / LRA 5.2 / Peak -1.4dBFS。
- **可复用结论**：**响度归一化是测量+补偿，不是设置。** 一遍出不来就两遍，第二遍必须喂第一遍的测量值。

### D9. `loudnorm` 默认把采样率升到 96kHz

- **现象**：交付件 aac 变成 96000Hz。
- **触发场景**：`loudnorm` 内部工作在 192kHz，输出时若没指定就保留高采样率。
- **当时的错误判断**：`-c:a aac` 会沿用源采样率。
- **正确做法**：显式加 `-ar 48000`。
- **可复用结论**：**任何滤镜链之后的编码，采样率都要显式声明。** 96kHz 的 aac 在部分播放器上直接没声音。

### D10. 起音密度检测器会饱和

- **现象**：参考片 11.28 次/秒、我们 11.12 次/秒，看着「已追平」，实际听感差很多。
- **触发场景**：10ms 窗能量正向差分 + 自适应阈值 + 8 帧冷却，检测上限约 12/秒。
- **当时的错误判断**：数字接近就是达标。
- **正确做法**：换指标——**脉冲对比度**（每 0.75s 窗口内 100ms 窗 RMS 最高-最低）与 **100ms 窗动态范围**（p10 到 p90）。这两个才区分「一直有声音」和「有节奏」。
- **可复用结论**：**指标饱和时，它测的已经不是你想问的东西。** 发现两个完全不同的样本给出相同数字，先怀疑指标失效。

## E. 交付层

### E1. Concat 混分轨不过母版链 → 轻 8.5dB

- **现象**：桥接导出件实测 I=-24.9 LUFS，而源 `score.wav` 是 -16.4。
- **触发场景**：分轨是母版链**之前**的信号，Concat 只做加法与 clip.volume。
- **当时的错误判断**：`suggestGain` 补偿过了就等价于母版。
- **正确做法**：交付前补一次 `ffmpeg -c:v copy -af "loudnorm=I=-16:TP=-1.5:LRA=9" -ar 48000`（视频流直接复制，不重编码）。
- **可复用结论**：**分轨之和 ≠ 母版。** 只要走「拆轨 → 剪辑器混音」这条路，最后必须补一次响度归一。

### E2. 字幕默认不烧进画面，但 `SUBS` 不会自动出现

- **现象**：`--subs-from-spec src/spec.mjs` 跑完没报错，导出件也没有字幕。
- **触发场景**：`spec.mjs` 里没有 `SUBS` 数组。
- **当时的错误判断**：桥接脚本会自己从 `CUE` 派生。
- **正确做法**：手写 `SUBS`，形态必须是 `[[起始秒, 结束秒, '文案']]`（`parseSubsFromSpec` 的正则只认这个）。缺了它，桥接读到空数组，静默通过。
- **可复用结论**：**「没报错」不等于「生效了」。** 涉及交付产物的开关，跑完要抽帧验证。

### E3. 字幕复述画面大字 → 重影

- **现象**：抽帧 `subs-20.jpg` / `subs-50.jpg` 里，画面左侧已有「若它在 1400 年爆发 / 我们要到 2040 年才知道」大字，底部字幕又打「我们要到 2040 年才知道」。
- **触发场景**：第一版把 10 句画面大字逐句搬进字幕轨（15 条）。
- **当时的错误判断**：字幕 = 画面的文字版。
- **正确做法**：**字幕只承担大字没说的连接词**，改 4 条：「光，要走很久」/「光在路上走了 640 年」/「那时它还没有爆发」/「中间隔着 640 年的沉默」。
- **可复用结论**：**同一句话在一帧里只能出现一次。** 字幕的职责是补足叙事，不是转写画面。

### E4. 不传 `--caption-bg` 就是无底色

- **现象**：需要「字幕底色透明」。
- **触发场景**：之前一直传 `--caption-bg "#05070AB8"`（半透明黑底）。
- **当时的错误判断**：要传一个「透明色」的值。
- **正确做法**：**不传这个参数**——`captionBg` 默认 `null`，桥接里是 `if (a.captionBg) style.background = a.captionBg;`，不传就不设 background。重跑后 `concat.json` 里 text clip 是 `"background": ""`。
- **可复用结论**：**「关掉某个效果」优先找「不传参数」，而不是「传一个表示空的值」。** 另一半教训在文档侧：示例命令里写着 `--caption-bg` 就会被人照抄，默认值必须体现在示例里。

### E5. Concat 工程的五条硬顺序

- **现象**：删轨不生效 / 音轨放错媒体 / 空轨复用编号。
- **触发场景**：直接用 MCP 工具手工编辑工程。
- **当时的错误判断**：编辑是幂等的，顺序无所谓。
- **正确做法**：①`project_save` **必须放所有编辑之后**（否则删轨只在内存）；②删空轨**必须在所有 clip 铺完后**（先删会让 `track_add` 复用编号）；③视频轨静音用 `clip_update` 的 `patch.muted`（不要 `detachAudio`）；④`edit_apply` 的参数是单数 `command` 不是 `commands` 数组；⑤`media_import` 返回的 `structuredContent` 同时含 `createdId` 和整个 `media[]`，遍历找 `m\d+` 会永远拿到已导入的视频——铺完轨要重新 `timeline_read` 按 `cl.media → mediaName` 逐条核对。
- **可复用结论**：**MCP 工具是有状态的 GUI 操作的投影，不是纯函数。** 顺序错了不会报错，只会静默做错。

### E6. `concat.lock` 残留

- **现象**：Concat GUI 报「工程已被占用」。
- **触发场景**：headless 进程异常退出。
- **当时的错误判断**：Concat 退出会自己回收锁。
- **正确做法**：桥接脚本在 `finally` 里无条件 `rmSync(join(projectDir, 'concat.lock'), { force: true })`。
- **可复用结论**：**外部进程留下的锁文件，清理责任在调用方。**

### E7. `export_start` 返 `{job}` 不是 `{jobId}`

- **现象**：轮询永远拿不到状态。
- **触发场景**：按常规 REST 习惯读 `jobId`。
- **当时的错误判断**：字段名应该是 `jobId`。
- **正确做法**：`export_start` 返 `{ job: "j1" }`，`export_wait` 只认 `job`。同理 `title_add` 的文案在 `style.content` 不在顶层 `text`（写错只得到占位符 "Your text"）；`clip_add` 的 `start` 是绝对秒（不传 `ripple` 会叠上去）。
- **可复用结论**：**每个 MCP 工具的返回结构都要实测一次再写代码。** 三个参数坑全是「名字像但是不对」。

## F. 文案与排版

### F1. 数字与单位要基线对齐，不是底边对齐

- **现象**：数字 y 770..812、单位 y 793..812，底差 1px，视觉上「单位吊在半空」。
- **触发场景**：两者都用同一个 `y` 当 `textBaseline = 'alphabetic'`，但字号不同。
- **当时的错误判断**：同一个 y 就是对齐。
- **正确做法**：单位 y 改 `readY - 1` 做视觉补偿；CJK 与数字混排时再单独校 4px 级差（CJK y 13..53 vs 数字 y 17..50）。
- **可复用结论**：**「同一坐标」只在同字号同字族时等于「对齐」。** 混排必须逐类校准。

### F2. `measureRun` 逐字摆放的字距偏差

- **现象**：CJK 逐字摆放后，字距与浏览器渲染的 `letter-spacing` 不完全一致（尤其标点与全角字符）。
- **触发场景**：为了做遮罩擦除，必须逐字 `fillText` 并累加 advance。
- **当时的错误判断**：`measureText(ch).width` 相加就等于整串宽度。
- **正确做法**：**用整串 `measureText(str).width` 作为布局基准**，逐字摆放只用于动画；两者不一致时以整串为准，把误差摊到字距里（`track` em 参数）。
- **可复用结论**：**排版宽度以整串测量为准，逐字测量只用于动画定位。** 逐字相加会累积 kerning 误差。

## G. 数据与诊断

### G1. 检测器硬编码路径导致传参被忽略

- **现象**：`sections.mjs` 传了两个不同文件，两次输出完全一样。
- **触发场景**：脚本里写死 `readFileSync('../../public/score.wav')`，`process.argv[2]` 根本没被读。
- **当时的错误判断**：输出一样说明两次内容确实一样。
- **正确做法**：改成 `process.argv[2] ?? '../../public/score.wav'`，并在输出里打印**实际读到的路径与文件大小**。
- **可复用结论**：**诊断脚本必须打印它实际读了什么。** 否则「两次结果相同」既可能是真相，也可能是 bug。

### G2. WAV 头不是 44 字节

- **现象**：解析 `loudnorm` 输出的 WAV 时 `RangeError: Invalid typed array length: -699747480`。
- **触发场景**：按「44 字节固定头」直接 `offset = 44` 读 data 区。
- **当时的错误判断**：WAV 头就是 44 字节。
- **正确做法**：从 `let off = 12` 开始逐块读 chunk id + size，跳到 `data` 块：
  ```js
  let off = 12;
  while (off < buf.length - 8) {
    const id = buf.toString('ascii', off, off + 4);
    const size = buf.readUInt32LE(off + 4);
    if (id === 'data') { off += 8; break; }
    off += 8 + size + (size % 2);
  }
  ```
- **可复用结论**：**WAV 是 RIFF 容器，头长度可变**（`loudnorm` 会写 `LIST`/`fact` 块）。任何「固定偏移」的假设都要先打印 chunk 列表验证。

### G3. 频谱质心 vs 八度带：后者才是可执行的判据

- **现象**：质心告诉我们「亮了一个八度」，但不知道该调哪个频段。
- **触发场景**：想用单一数字指导 EQ。
- **当时的错误判断**：质心接近就说明音色接近。
- **正确做法**：用**八度带能量分布**（40/80/160/320/640/1280/2560/5120/10240/20000Hz 边界，4096 点 FFT）逐带对比，直接读出「40–80Hz 少 30.7%、160–320Hz 多 24.4%」，EQ 就有了明确目标。
- **可复用结论**：**诊断指标要能直接映射到一个可调参数。** 质心是「结论」，八度带是「处方」。

### G4. 声画对位的判据要能区分「本来就在响」

- **现象**：27 个画面动作里 7 个始终「无响应」，加大音量会破坏「每格一个音」的平衡。
- **触发场景**：判据是「该时刻 0.25s 窗 RMS 比前 0.5s 高 3dB」，但如果前一窗正好落在网格脉冲上，它本身就很响。
- **当时的错误判断**：无响应就是漏了音效。
- **正确做法**：接受这 7 个为**取舍**而非遗漏——要压过前一窗的脉冲，就得把事件音量提到破坏脉冲平衡的程度。最终 17 咬住 / 3 弱 / 7 无响应，并在汇报里写明这是取舍。
- **可复用结论**：**对位检测给出的是「相对抬升」，不是「绝对有无」。** 有节拍网格的片子里，一部分画面动作天然无法产生相对抬升，这是设计约束不是缺陷。

## H. 仓库与同步

### H1. 工作区不是 git 仓库，交接文档在仓库外

- **现象**：`git status` 报 `fatal: not a git repository`。
- **触发场景**：在 `Vibe知识大赏/` 根目录跑 git 命令。
- **当时的错误判断**：整个工作区是一个仓库。
- **正确做法**：`motion-ledger/` 才是仓库（`main` / `origin git@github.com:boosn1/motion-ledger.git`）；`motion-ledger-HANDOVER.md` 在工作区根、**仓库外**，因此不在 git 管理范围。要让它进版本控制，必须移进仓库或另建仓库。
- **可复用结论**：**先确认「哪个目录是仓库」，再谈提交。** 文档放在仓库外 = 永远不会被同步。

### H2. `publish.mjs` 不同步 dsh skill 目录

- **现象**：推送成功，但 `D:\Users\boosn\.dsh\skills\motion-ledger` 还是旧版。
- **触发场景**：以为 `publish.mjs` 会顺带同步安装目录。
- **当时的错误判断**：发布 = 推送 + 安装。
- **正确做法**：`publish.mjs` 只做「跑门禁 → 查悬空引用 → 提交 → 推送」四件事；同步要手工：
  ```powershell
  $dst = Join-Path $env:DSH_HOME "skills\motion-ledger"   # 本机 DSH_HOME 在 D 盘
  git ls-files | ForEach-Object { Copy-Item $_ (Join-Path $dst $_) -Force }
  ```
- **可复用结论**：**「发布」和「安装」是两件事，各有一份真相。** 推送后必须核对两边的文件数一致（本机实测 50 vs 50）。

### H3. 三份 `score.mjs`，`sync.mjs` 只比两份

- **现象**：模板两份一致（35,062 字节，sha `48446E2DFCDA`），项目里那份 41,964 字节（sha `7600CE6FAD1B`）多出 ducking / stereoize / fadeTail / 新母版链。
- **触发场景**：在项目里改进了 `score.mjs`，没回写模板。
- **当时的错误判断**：`verify/sync.mjs` 通过 = 全部一致。
- **正确做法**：`sync.mjs` 只比 `templates/remotion-starter/scripts/score.mjs` 与 `templates/node-starter/scripts/score.mjs`；项目内的第三份不在它的视野里。项目侧的改进要单独决定是否回写模板（回写会让所有新项目继承，但也可能带进未验证的参数）。
- **可复用结论**：**「同步脚本通过」只覆盖它检查的那两份。** 项目派生出的第四份、第五份，要有人负责判断回流。
