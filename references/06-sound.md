# 06 · 声音

**默认有声音。** 用户没说要静音，就有声音。

弱模型最常见的偷懒：全片静音，或者拿噪声当音乐。两个都会被门禁抓。

---

## 三条决定，分开做

| 决定 | 内容 | 谁定 |
|---|---|---|
| **voice** | 有没有旁白 / 配音 | 提示词有台词才有 |
| **music** | 有没有音乐床 | 默认有 |
| **effects** | 有没有音效 | 每个视觉打击都要有 |

**「不要旁白」只禁语音，不禁音乐音效。**
**显式静音请求优先**（"要静音""不要声音"）→ 全片静音，且 `FILM.sound = false`。

---

## 音乐规格

### 结构

```json
{
  "duration": 15,
  "bpm": 120,
  "loop": true,
  "palette": ["pluck", "pad", "tick"],
  "bed": [
    { "at": 0, "dur": 15, "inst": "pad", "notes": [220, 277.18, 329.63] }
  ],
  "patterns": [
    { "inst": "pluck", "every": 0.5, "notes": [440, 554.37, 659.25], "from": 0, "to": 15 }
  ],
  "events": [
    { "at": 1.4, "inst": "tick", "gain": 0.5 },
    { "at": 3.2, "inst": "whoosh", "gain": 0.6 }
  ]
}
```

### 规则

- **音乐必须来自有音高的乐器**（pluck / bell / pad / kick 有音高）。
- **噪声只做点缀，且 < 1s**（whoosh / scratch）。
- 环境主导的场用 `ambience` 床（rain / wind / room），不要拿音乐压环境。
- **既无音乐也无 ambience 时，脚本拒绝出谱**——这是硬门禁，不是建议。

### 乐器

```
pluck / bell / pad        有音高，做床与乐句
ambience(rain|wind|room)  环境床
tick / kick / clap / hat  节奏
whoosh / drop / knock / scratch / boom  点缀（< 1s）
```

---

## 音效对齐

**每个视觉打击都要有声音，且落在同一个时间点。**

音效时间**从时间线事件表派生**，不要手写第二份时间表——那样一定会漂。

```
事件表 t=1.40s: E02 标题逐字入场
  → cues.json events: { at: 1.40, inst: "tick" }
```

对齐误差容忍 **≤ 3 帧**（60fps 下 50ms）。超了就是"音画不同步"，观众能感觉到。

---

## 循环

`loop: true` 时：

1. 音乐尾部的余韵**折进开头**（不要硬切）。
2. 音频总长必须**等于**视频总长。
3. 末帧音频电平与首帧接近（不要结尾突然静音）。

## 响度

母版目标 **-14 LUFS**（流媒体标准）。

```bash
ffmpeg -i raw.wav -af loudnorm=I=-14:TP=-1.5:LRA=11 -ar 48000 out/score.wav
```

- `I=-14`：整体响度
- `TP=-1.5`：真峰值上限，防削波
- `LRA=11`：响度范围

### 但「-14 LUFS」是给流媒体平台的，不是给人戴着耳机看的

上面的 loudnorm 是**上传到 B站/YouTube 前**该做的事——平台会做响度归一化，送 -14 LUFS 进去才不会被压。

问题是**本地看片的时候没人做归一化**。-14 LUFS 的配乐配一支没有旁白的片子，听感是「一直在往外推」。实测用户反馈两次：

| 版本 | mean_volume | 反馈 |
|---|---|---|
| v1 | -21.4 dB | 「BGM 音量有些小」 |
| v2 | -18.6 dB | 「pod 音量还是有些大，-20dB 好一点」 |
| v3 | **-20.3 dB** | 接受 |

**-20 dB 左右是「没有旁白、纯配乐」这类片的舒服区间**。-14 LUFS 换成 mean_volume 大约在 -14 ~ -16 dB，比这个响 4–6dB。

所以分两种交付：

- **要发平台**：`loudnorm=I=-14` 出一版，交给平台归一化。
- **自己看/给客户审**：**-20 dB 左右**。这支片是后者。

调整方法（不要重跑 score.mjs，那是改配乐本身）：改 `Film.tsx` 里 `<Audio>` 的 `volume`。

```tsx
// Remotion 渲染固定压掉约 3.2dB（实测 score.wav peak 0.890 → 成片 0.614）
const MASTER_VOL = 1.19;   // 1.45 → 1.19，交付件从 -18.6 降到 -20.3 dB
```

`volume` 与 dB 的换算：`volume = 10^(降幅dB / 20)`。要再降 1.7dB → `1.45 / 10^(1.7/20) ≈ 1.19`。

> **别用「改 score.wav 的归一化系数」来调音量。** 那改的是配乐内部各层的相对平衡，不是整片电平。整片电平是交付环节的事，在 `Film.tsx` 一处改。

## 常见失败

| 失败 | 症状 | 修法 |
|---|---|---|
| 默认静音 | 全片无声 | 加 pad 床 + 事件音效 |
| 拿噪声当音乐 | 嘶嘶声铺满 | 换成有音高的乐器 |
| 打击不对拍 | 音效比画面晚 | 从事件表派生，不手写 |
| 音效太响 | 盖过音乐 | `gain` 降到 0.3–0.6 |
| 结尾硬切 | 循环接缝有咔哒 | 尾部折进开头 + 淡出 |
| 响度太低 | 手机听不见 | loudnorm 到 -14 LUFS |
| **嗡嗡像电流** | 背景一层闷响，听久了头胀 | 见下一节——这是频谱问题，不是音色问题 |
| 节奏像没睡醒 | 明明 BPM 对，就是不动 | 见「律动感」一节——密度不够，不是速度不够 |

## 「嗡嗡像电流」——本方法最容易踩的音质坑

代码合成的铺底如果只堆**纯正弦**，听感就是电流嗡鸣。它有三个独立成因，必须一起修：

**成因一：低频能量失衡。** 实测一支 60 秒科普片的原始配乐，20–80Hz 占 37%、80–250Hz 占 59%、250Hz 以上只有 3.7%。人耳在 250Hz 以下几乎分不出音高，只感到「压力」——能量全堆在那儿，听起来就是一堵墙在嗡。

修法是母版链，不是改音色：

```js
biquad(buf, 'highpass', 95, SR, 0.8);      // 95Hz 以下清掉，嗡鸣主战场
biquad(buf, 'peak', 160, SR, 1.1, -2.5);   // 160Hz 那点闷声压 2.5dB
biquad(buf, 'highshelf', 3200, SR, 0.7, 2.0); // 3.2k 以上抬 2dB，补回清晰度
```

修完同一支片：sub 从 37% 降到 2.1%，mid（250Hz–2k）从 3.7% 升到 95.5%。这才是「音乐」。

**成因二：长音被切片。** `bed` 里 `pad` 这类持续音如果按「2 秒切片循环铺」实现，包络每 1.7 秒重启一次——听感就是周期性的「一涌一涌」，和嗡鸣叠在一起特别难受。持续音要**一次铺满整段**，用 sustain 包络（起音 0.35s，不衰减，收尾 0.35s 淡出）。只有 `pluck`/`bell` 这类衰减型才切片。

**成因三：单频正弦没有厚度。** 一个频率一个正弦 = 一根针。真实乐器每个音都是多路微失谐叠加。pad 至少三路（±0.35%）+ 一路非谐波泛音（4.7 倍），才有「气」而不是「嗡」。

**判断方法**：不要靠听。跑频谱占比，sub 超过 20% 或 mid 低于 20% 就是失衡，与音色无关。

## 律动感——为什么 BPM 对了还是「慢」

BPM 决定的是**网格**，律动感决定的是**网格上的密度**。80 BPM 的 8 分音符是 0.375s，16 分是 0.1875s——同一个 BPM，密度可以差四倍。

一支 60 秒科普片原本只有一条 `pluck` 每 3.0 秒响一次（80 BPM 下的 4 拍一个音），等于整片只有 11 个音符。BPM 80 没写错，但观众听到的是「散点」不是「节奏」。

改法（不改 BPM，因为画面事件是按它排的）：

| 层 | 原来 | 改成 | 作用 |
|---|---|---|---|
| 旋律 | `pluck` 每 3.0s | `pluck` 每 0.375s（8 分音符），八音音阶循环 | 从散点变成走句 |
| 低频 | 无 | `kick` 每 0.75s（每拍） | 给每拍一个「落地」 |
| 高频 | 无 | `hat` 每 0.375s（8 分） | 给八分音符一层「沙」，速度感主要来自这里 |
| 强调 | 无 | `clap` 落在段落节点（18.0 / 21.0 / 33.0 / 42.0） | 标出「这一句完了」 |

改完 `patterns` 从 1 条变 5 条，`events` 从 56 个变 63 个。

**关键纪律：改节奏型不能改 BPM。** 画面事件（元素入场、变形起止、字幕切换）是按 `60/BPM` 的整数倍排的，改 BPM 会让全部事件脱离拍点，`film.mjs` 的峰值声明区间也会跟着失效。**要更密，加密音符；要更快，那是在改片子结构，不是在改配乐。**

## 「缺一个 BGM」——BPM 和密度都对了，还是不像一首曲子

这是比律动更深一层的问题，而且**用耳朵很难定位**：你会觉得「少了点什么」，但说不出少什么。答案通常是**和声没有走**。

### 怎么测：和声变化次数

一段音乐如果整分钟都在同一组音上，它听感就是 drone（持续低音），不是曲子。这个可以量：

1. 把音频切成 8 段，每段算 12 个音级（pitch class，C/C#/D…）的能量分布——Goertzel 扫 MIDI 45–81 就够，不需要 FFT 库
2. 每段取最强的 3 个音级，得到 8 组三音集合
3. 统计相邻两组的差异个数之和 = **和声变化次数**

实测参考（同一套算法，取前 60 秒）：

| 曲目 | 和声变化次数 | 判读 |
|---|---|---|
| 抖音热门 BGM（紧张氛围） | 8 | 约每 7 秒换一个和弦 |
| 抖音热门 BGM（钢琴怀疑） | 9 | 同上 |
| 另一个自制的 numpy 配乐 | 3 | 循环太短，四小节就回去了 |
| **本方法的初版** | **0** | 整片一组 A 大三和弦，就是 drone |

### 怎么改：给 `cues.json` 加 `chords` 段

```json
"chords": [
  { "at": 0,  "dur": 6, "inst": "pad", "notes": [220, 261.63, 329.63], "gain": 0.175 },
  { "at": 6,  "dur": 6, "inst": "pad", "notes": [174.61, 220, 261.63], "gain": 0.175 }
]
```

三件事必须一起做，少一件就不成立：

1. **`chords` 是独立的一段，不要塞进 `bed`。** `bed` 管「一个音色铺多久」，`chords` 管「和声走到哪」。一个和弦可以跨两个 bed，一个 bed 也可以盖三个和弦。混在一起，改和声就得改 bed。
2. **每个和弦多给 0.5s（`tailOverlap`），并且 `pad` 的包络要真的淡出。** 不交叠、不淡出，换和弦那一瞬间会掉到零，听感是一个「抽气」。`pad` 的 `release` 必须是 `Math.max(0, Math.min(1, (dur - t) / 0.35))` 这种无条件淡出——早期为了防切片起伏写成 `dur > 2 ? 1 : ...`（长音不淡出），一旦开始换和弦就会硬切。
3. **补低音声部（`bass`）**，但**必须带泛音**：`0.62*sin(hz) + 0.26*sin(2hz) + 0.12*sin(3hz) + 0.05*sin(4.02hz)`。纯正弦在 80–130Hz 就是电流声，这正是「嗡嗡像电流」的成因之一。

### 加完和弦会掉进的新坑：频带又失衡了

和声进行要求 pad 铺得够宽，但 pad 的基频（146–392Hz）落在 **low** 频段，加进来 mid 反而更空。实测：只加 `chords` + `bass`，mid 从 3.4% 掉到 3.4%、low 冲到 78.7%——嗡鸣判据（mid < 20%）直接命中。

**解法是给和弦再叠一层高八度的 pad**（`notes` 每个 ×2，gain 约 0.135）。高八度把能量直接推进 250–2k：

| 阶段 | sub | low | mid |
|---|---|---|---|
| 只有 pad + 和弦 + bass | 17.8% | 78.7% | 3.4% |
| 和弦 ×0.88 + bass ×0.82 + 高八度层 0.115 | 14.6% | 66.3% | 19.0% |
| 高八度层 0.135 + bass ×0.85 | **13.9%** | **62.9%** | **23.0%** |

判据：**sub > 20% 或 mid < 20% 就是失衡**。改完最强频点从 `108Hz`（drone）变成 `218Hz`（A3，是音乐里的音），这是「从机器在响变回音乐」的频谱证据。

### 16 分网格堆积不是 bug

改完律动后仍有一个指标偏高：16 分网格上 47.5% 的起音能量砸在同一格（参考曲 41.8%）。查过是 `kick` 在位 0/4/8/12、`pluck` 在位 1/3/5/7，而位 3 是旋律里的 A4——**正好是根音**。根音落在强拍是音乐上的正确行为。别为了把数字压到参考值而破坏和声。

## 拿参考曲当标尺：一套可复现的配乐调音流程

前面几节都是「发现问题 → 修」。这一节是反过来：**先量参考曲，再按数字配自己的**。用户给了一支喜欢的 BGM 说「照这个来」时走这条。

前提：参考曲只做**离线测量**，不复用任何一个采样。这是合规的——测 BPM、频谱、包络不是使用作品。参考做法见另一个项目 `音频来源与许可.md` 的写法：「本片没有任何第三方采样或曲库素材」「仅做 BPM/电平/语速离线测量，未复用任何一秒」。

### 三个测量脚本（零依赖，只用 numpy）

**① 八度带能量占比**——回答「厚度够不够」

按 20–40 / 40–80 / 80–160 / 160–320 / 320–640 / 640–1280 / 1280–2560 / 2560+ 切带，算各带功率占总功率的比例。用 8192 点 FFT、50% 重叠、汉宁窗累加。

**② 每带包络的 CV（变异系数）与峰均比**——回答「低频是打出来的还是铺着的」

逐 20ms 窗求该带幅度，得到包络序列，算 `CV = std/mean` 与 `p95/p50`。判读：

- `CV > 0.5` → **脉冲**（随拍打出来的）
- `0.25 < CV ≤ 0.5` → 半脉冲
- `CV ≤ 0.25` → **常驻 drone**

**这一条是整个流程里最关键的判断。** 低频重不重不是问题，低频是打出来的还是铺着的是问题。

**③ 和声变化次数**（上一节讲过）+ 频谱质心走向 + 16 分网格起音分布

### 一份实测对照（同一套算法）

| 频段 | 参考曲 | 我们的初版 | 我们的成品 |
|---|---|---|---|
| 20–40Hz | 26.5% | 6.9% | **24.6%** |
| 40–80Hz | 44.9% | 70.3% | 28.0% |
| 80–160Hz | 15.7% | 9.0% | **24.0%** |
| 160–320Hz | 5.6% | 5.2% | 8.3% |
| 640–1280Hz | 1.4% | 1.6% | 2.8% |
| **30–80Hz 的 CV** | **0.65** | 0.98（但占比 0.0%） | **0.99** |
| **80–160Hz 的 CV** | **0.92** | 0.48 | **0.89** |
| RMS | -19.2 dBFS | -20.3 dBFS | -18.4 dBFS |
| crest（峰均比） | 15.5 dB | 19.3 dB | 17.4 dB |

初版那一列暴露了两个真问题：**80Hz 以下占 0.0%（薄）**，而 **160–400Hz 占 29.2%、400–1200Hz 占 41.4%（中频过载）**。参考曲恰好在这两个频段最少（5.6% + 5.4%）。中频堆满 = 听起来薄、亮、廉价。

### 五步改法

**第一步：`kick` 改成三层。** 单正弦扫频只有「噗」，没有「咚」。

```js
kick(t, dur, hz, gain) {
  const env = Math.exp(-t / 0.15);
  const f = 42 + 130 * Math.exp(-t / 0.028);      // body：扫频落到底
  const body = Math.sin(TAU * f * t);
  const thump = 0.55 * Math.sin(TAU * f * 0.5 * t); // thump：半频，20–60Hz 胸口感
  const click = Math.exp(-t / 0.008) * 0.22 * Math.sin(TAU * 2600 * t); // click：打的瞬态
  return gain * (env * (body + thump) + click);
}
```

三层分工：body 负责音高、thump 负责胸口、click 负责「打」这个动作。少一层就不像鼓。

**第二步：`sub` 只进 `patterns`，绝不进 `bed`。** 这是全流程最重要的一条纪律。同样一个 55Hz 正弦，按拍打出来是低音，长音铺满整段就是电流声。

```js
sub(t, dur, hz, gain) {
  const attack = Math.min(1, t / 0.012);   // 12ms 起音，不是 4ms
  const env = Math.exp(-t / 0.24) * attack;
  const v = Math.tanh(2.2 * Math.sin(TAU * hz * t)) / Math.tanh(2.2); // 软饱和长出谐波
  return gain * env * v;
}
```

起音 12ms 而不是 4ms 有实测原因：4ms 等于瞬间跳变，crest 会冲到 19dB 以上，归一化被迫压到 ×0.58，整片平均音量反而变小。参考曲 peak 只有 -3.7 dBFS 却更响，因为它靠压缩提 RMS，不靠推增益。

**第三步：`bassPluck` 补 80–160Hz 的强脉冲。** 参考曲这一段 CV 0.92（峰均比 4.39），是底鼓二次谐波加贝斯打点的混合。用 `bass` 长音去做这一段，CV 会掉到 0.4 以下，听感糊成一片。

**第四步：母版链改成「不砍低频」。** 这是被实测推翻两次的地方，写清楚免得再走回头路：

```js
function masterChain(buf, sampleRate) {
  biquad(buf, 'highpass', 30, sampleRate, 0.7);          // 30Hz 以下只有隆隆声，切掉无损
  biquad(buf, 'peak', 260, sampleRate, 1.0, -3.5);       // 160–400Hz 中低过载，压 3.5dB
  biquad(buf, 'peak', 750, sampleRate, 1.2, -2.0);       // 400–1200Hz 再压 2dB
  biquad(buf, 'highshelf', 2400, sampleRate, 0.7, 2.5);  // 高频抬回清晰度
  limiter(buf, sampleRate);                              // 软限幅收 crest
  return buf;
}
```

> **走过的弯路**：早期为了修「嗡嗡像电流」，用 `highpass 95Hz` 一刀切。嗡确实没了，**厚度也没了**——这是用户下一轮说「还是不行」的真正原因。问题从来不是低频太多，是低频全是持续音、没有打点。判断口径应该是 CV，不是占比。

**第五步：加一级软限幅。** 2:1 软拐点、阈值 -16dBFS、attack 4ms / release 120ms。低于阈值完全不动（保住打点的瞬态），高于阈值每 2dB 只留 1dB。

效果实测：crest 19.1 → 17.4 dB，归一化系数 ×0.58 → ×0.98，RMS -20.1 → -18.4 dBFS。**同一份内容，听得见的响度提升了一档半。**

### 调音的目标值（不是抄数字，是抄关系）

| 指标 | 目标 |
|---|---|
| 20–160Hz 合计 | ≥ 70%（厚度） |
| 160–400Hz | ≤ 12%（中低过载 = 廉价感） |
| 400–1200Hz | ≤ 15%（中频过载 = 薄、亮） |
| 30–80Hz 的 CV | ≥ 0.5（脉冲，不是 drone） |
| 80–160Hz 的 CV | ≥ 0.7（强脉冲） |
| crest | 15–18 dB |
| RMS | -20 ~ -18 dBFS |

**这些数字不是硬指标，是「和参考曲同一种听感」的坐标。** 换参考曲要重新测，不要套用。

### 每次做新片子的固定动作

1. 用户给了参考曲 → 先跑三个测量脚本，记下八度带占比、各带 CV、crest、RMS
2. 拿自己的 `score.wav` 跑同一套，把两张表并排看
3. 按上面的五步改（先改音色，再改母版链，最后调 gain）
4. **改完必须重量**，别凭耳朵判断「应该好了」
5. 数字对齐了再重渲、跑门禁、交付

用户没给参考曲时，用本节的目标值表当默认基线。

## 两个「听起来像电流声」的真凶（都不是「噪声太多」）

这两条是用户连着两轮反馈「嗡嗡的电流声」之后，靠频谱分析才挖出来的。它们和「低频占比」「和声够不够」都没关系，但听感上都会被描述成「电流声」。

### 真凶一：`sub` 写在了人耳听不见的频率上

`cues.json` 里 sub 层写的是 **24.5Hz / 27.5Hz / 36.71Hz**。人耳下限约 20Hz，但**多数音箱在 40Hz 以下根本推不出声**——它只会把这段能量变成纸盆的机械振动，听起来是「隆隆」的闷响，不是音高。

更糟的是它**吃掉归一化额度**：峰值检测看的是波形绝对值，24.5Hz 那个大幅度慢波就是全片峰值，于是 `normalize` 只能把整片压到 ×0.90，音乐部分跟着被压小。这就是「电流声盖过 BGM，BGM 音量小」的完整因果。

**判据**：跑一次八度带占比，看 `0–25Hz` 和 `25–40Hz`。合计超过 10% 就是有问题。

| | 修前 | 修后 |
|---|---|---|
| 0–25Hz | — | 0.36% |
| 25–40Hz | ~30% | 4.09% |
| 40–60Hz | — | 34.21% |
| RMS | -21.4 dB | **-18.8 dB** |

**改法**：sub 层所有音符抬到 **≥40Hz**（E1 41.2 / F1 43.65 / G1 49 / A1 55 / C2 65.41 / D2 73.42），母版链 `highpass` 从 30Hz 提到 **38Hz**。低八度的加成 gain 从 0.62 降到 0.42——低频托底靠 40–80Hz 的**打点**，不靠更低的音。

### 真凶二：噪声音色吐的是全频白噪声

`hat` / `tick` / `clap` / `whoosh` / `scratch` / `ambience_*` 这六个音色的源码里写着「一阶差分近似高通」，**但代码里根本没有差分**——`return gain * env * n * 0.5`，`n` 是 `rnd()*2-1`，就是白噪声。

60 秒里 hat 响 120 次、tick 响 33 次，叠加成持续的「嘶——」。

**判据：频谱平坦度**（spectral flatness = 功率谱几何均值 / 算术均值）。白噪声 ≈ 1.0，乐音 < 0.1。逐音色隔离跑一遍就能一眼看出谁在吐噪声：

| 音色 | 80–160Hz | 160–320Hz | 320–640Hz |
|---|---|---|---|
| `hat`（修前） | **0.726** | **0.651** | **0.602** |
| `pad` | 0.043 | 0.060 | 0.007 |
| `bass` | 0.037 | 0.006 | 0.000 |

**改法**：给 `addNote` 传一个**每音符私有**的滤波状态对象 `st`，然后

- 一次差分（6dB/oct）：`const hp = (n0 - n1) * 0.5; st.prev = n0;` —— 用于 `tick` / `whoosh` / `scratch` / `ambience_rain` / `ambience_wind`
- 二次差分（12dB/oct）：`const hp = (n0 - 2*n1 + st.prev2) * 0.35;` —— 用于 `hat` / `clap`
- **例外**：`ambience_room` 反而要做**低通**（`lp = st.prev * 0.985 + n0 * 0.015`），因为房间底噪本来就是低频的，高通会把它变成嘶声

差分会损失能量，`hat` 的系数要从 0.5 提到 1.6 补偿。

> **教训**：注释写「高通」不等于代码做了高通。这类「注释与实现不符」的 bug，靠读代码看不出来（注释是自洽的），只能靠**测量**抓——所以 `score.mjs` 改动后必须跑一次频谱平坦度。

### 定位方法：先分轨，再听

上面两个真凶都是靠「哪一层在响」定位的，不是靠猜。**所以配乐出问题时，第一个动作是分轨，不是重调参数。**

```bash
node scripts/score.mjs --cues scripts/cues.json --out public/score.wav --stems
```

它按「耳朵能分辨的层」导出九条独立 WAV，并打一张占比表：

```
  层          峰值dBFS   RMS dBFS   占比
  pad           -8.9    -22.7    14.5%
  bass         -19.5    -30.3     2.5%
  sub           -7.8    -18.2    41.0%
  bassPluck     -7.0    -21.3    20.0%
  kick           1.5    -21.9    17.6%
  hat          -19.8    -45.0     0.1%
  pluck        -18.5    -34.6     0.9%
  perc          -6.6    -29.0     3.4%
```

**这张表就是诊断结论**：81% 的能量压在低频四层（sub + bassPluck + kick + bass），`pad` 只有 14.5%——「嗡嗡」只可能来自那四层，`pad` 和 `pluck` 无罪。反过来，如果 `hat` 占比异常高，就该去查噪声高通（真凶二）。

要看逐轨试听，把分轨铺进 Concat（一层一条轨，可逐轨静音）：

```bash
node scripts/concat-bridge.mjs --film out/film.mp4 --stems public/stems \
  --subs-from-spec src/spec.ts --out final.mp4
```

细节见 `08-delivery.md` 的「分轨工程」一节。

### 真凶三：持续音被切片重触发（bass 没进 `isSustain`）

`synth()` 的 bed 分支把「衰减型」音色按 `slice*0.85`（1.7 秒）切片循环铺。`isSustain` 名单里当时只有 `pad` 和 `ambience`，**`bass` 不在里面**——于是 6 秒的 bass 床被切成 1.7 秒一段，每段重新起音、重新淡出。

调制谱上就是 **0.588Hz（= 1/1.7）的强峰**。低频上的周期性起伏，人耳读成「一台泵在推音量」，也就是「嗡嗡」。

**判据：看 20ms 窗 RMS 包络的调制谱**。把包络去均值后做 DFT，找 0.2–12Hz 的峰：

| 层 | 修前主导调制 | 修后 |
|---|---|---|
| `pad` | 1.00 / 1.50 / 2.00 Hz | 0.20 / 0.30 / 0.50 Hz |
| `bass` | 0.50 / 0.60 Hz | 0.50 Hz（仅换音） |

**1–4Hz 是「嗡」的频段**，0.2–0.5Hz 是「呼吸」。同一个包络缺陷，落在哪个频率决定了它听起来是音乐还是故障。

修法两条：

1. **`isSustain` 加上 `bass`**（判据：凡是「长音、有音高、要一直响」的音色都属于持续音；凡是「打一下就没」的 `pluck`/`bell`/`tick`/`kick` 才该切片）。
2. **持续音的包络必须是平的**，只有起音和收尾。曾经写过 `0.55 + 0.45*exp(-t/3.0)` 的慢衰减，本意是「别太死」，但每个音重新起算，6 秒一换音就等于每 6 秒把音量拉回满格再放掉 39%——一列锯齿波，调制谱上 0.167/0.33/0.5Hz 三个峰（0.5 是它的三次谐波）。**真正让长音不死的办法是换音（和声走），不是靠包络衰减。**

顺带修掉一个同源问题：**`pad` 的失谐量太大**。原来是 ±0.35%，在 220Hz 上产生 1.45Hz 的拍频（`220×1.0035 - 220×0.9969`），调制谱上就是 1.0/1.5/2.0Hz 三个峰——听感是「颤」。收到 ±0.07% 后拍频 0.31Hz（周期 3.2 秒），才是 chorus 该有的呼吸感。同时去掉了原来的 4.7 倍非谐波分量：非谐波 + 失谐叠在一起最像「电流」，纯谐波（1/2/3 倍）才有音高感。

> **教训**：低频「嗡」几乎从来不是「低频太多」，而是**低频的包络在 1–4Hz 上周期性起伏**。所以判断嗡不嗡，看的是包络的调制谱，不是频谱的频带占比。

### 顺带发现：Remotion 渲染会固定压掉 3.2dB

同一份 `score.wav`（RMS -18.8 dBFS、peak 0.890）渲进 `film.mp4` 后变成 **RMS -21.8 dBFS、peak 0.614**——固定的 3.2dB 衰减。

**改法**：`<Audio src={staticFile('score.wav')} volume={1.45} />`（10^(3.2/20) ≈ 1.45）。改完实测成片 RMS -18.6 dBFS，与源文件一致。

**别用「把 score.wav 音量推高」来解决**——那会让 wav 本身削顶，而衰减发生在渲染环节，推高源文件只是把削顶藏起来。

### 层音量：在剪辑器里调，抄回 `cues.mix`

分轨铺进 Concat 之后，最容易发生的事是：**作者在时间线上拖了几下滑杆，觉得平衡对了——然后重新生成，全没了。**

滑杆只活在工程文件（`concat.json` 里每条 clip 的 `volume`）里，`score.wav` 和分轨 WAV 都不知道它。所以试听调出来的平衡必须**抄回 `cues.json`**：

```json
"mix": {
  "pad": -31.6
}
```

单位是 dB，相对**该层原始电平**。`-31.6` 就是「pad 这一层整体降 31.6 dB」，其余层不写 = 0 dB。

**为什么必须乘在合成阶段，而不是只乘分轨**：只在剪辑器里压分轨、母版不动，会得到「试听版安静、交付版仍吵」的分裂——你听着舒服的那一版不是发出去的那一版。写进 `cues.mix` 后，`synth()` 在 `addNote` 里对每个采样乘 `10^(db/20)`，**母版 `score.wav` 与分轨 WAV 同时按这个平衡合成**，两边一致。

实现（`score.mjs` 的 `synth()`）：

```js
const MIX_GAIN = {};
for (const b of BUS_ORDER) {
  const db = mix[b];
  MIX_GAIN[b] = Number.isFinite(db) ? Math.pow(10, db / 20) : 1;
}
// addNote 内
const v = fn(i / SR, durSec, hz, gain, rnd, st) * (MIX_GAIN[busName] ?? 1);
```

#### 从工程文件反读滑杆值

Concat 的滑杆是 **dB 刻度**，落到 clip 上是线性倍数。用户在 −30 dB 位置停下，写进 `concat.json` 的就是 `0.0316227748990059`：

```
0.0316227748990059 ≈ 10^(-1.5) = 10^(-30/20)
```

所以反读公式就是 `dB = 20 * log10(volume)`。但要注意**基准不同**：

- 其它分轨的 `volume` 是 `1.19654`（`stems.json` 的 `suggestGain` 补偿量，不是 1）
- 所以 `pad` 相对其他层的真实差值不是 −30 dB，而是 `20*log10(0.0316228 / 1.19654) = -31.56 dB`

**读工程文件时先看同一工程里其他轨的 volume 是多少**，别拿绝对值当 dB 用。

#### 固化之后工程里就不再需要滑杆补偿

pad 的 −31.6 dB 已经在 WAV 里了，所以重建工程时 8 条分轨的 `volume` 全部是同一个值（`1.175983`，即新的 `stems.json` 补偿量）。工程文件里不再有单独被拖低的那一条——**这不是「调音丢了」，而是调音进了源料**。

验证方法：看 `score.mjs` 的输出，会多一行

```
层音量（cues.mix，合成阶段生效，母版与分轨同时受影响）：
  pad         -31.6 dB
```

以及分轨表里 `pad` 的占比会掉到 0.0%（实测 `-45.1 dBFS 峰值 / -60.3 dBFS RMS / 0.0%`）。

#### 判断「这一层是不是该压」

分轨表的「占比」列按 RMS² 算（真实功率占比）。实测这一版：`sub 48.1% / bassPluck 23.5% / kick 20.6% / perc 4.0% / bass 2.8% / pluck 0.9% / hat 0.1% / pad 0.0%`。pad 原本占 14.7%，压到 0.0% 后整片 `mean_volume` 只从 −21.8 降到 −22.5 dB——**说明它本来就是垫底的一层，压掉它不改变响度，只改变「糊」的程度**。这正是用户说「pad 是嗡嗡罪魁」的量化解释。

## 何时用真配乐

代码合成的音色是**简单**的。如果用户明确要求音乐质量：

> 如实告知：本方法产出的是代码合成配乐，音色简单。要求高的建议后期替换为真实配乐，时间线不变（`cues.json` 的 `events` 就是替换时的对齐表）。

不要假装合成配乐能达到商业音乐水准。
